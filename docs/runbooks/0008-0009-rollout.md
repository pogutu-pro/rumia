# Runbook: apply migrations 0008 and 0009 to production

Production is on revision `0007`. `main` already serves the email-code and password sign-in endpoints, which need the
tables from `0008` and `0009`; until they exist those endpoints fail.

## What the migrations do

| Revision | Change | Risk |
|---|---|---|
| `0008` | New table `auth_email_codes` and one index | Additive, `IF NOT EXISTS`, no existing table touched |
| `0009` | New table `auth_credentials` (FK to `auth.users`), new nullable column `auth_email_codes.pending_password_hash` | Additive; the `ALTER` is on the table `0008` just created, so no lock on live data |

Both downgrades only drop what they created. Google sign-in does not use either table.

## 1. Back up (on the server)

```bash
cd ~/rumia
docker exec rumia_postgres pg_dump -U rumia -d rumia -Fc --no-owner > ~/backups/rumia_pre0008_$(date -u +%Y%m%dT%H%M%SZ).dump
ls -lh ~/backups | tail -3        # the new dump must be non-empty
docker compose exec -T backend alembic current   # expect: 0007 (head is 0009)
```

## 2. Rehearse on a restored copy (on a machine with Docker, never production)

```bash
scp <server>:~/backups/rumia_pre0008_*.dump /tmp/
scripts/restore-snapshot.sh /tmp/rumia_pre0008_*.dump
cd backend
DATABASE_URL=postgresql+asyncpg://postgres:pw@localhost:5555/rumia_restore uv run alembic current    # 0007
DATABASE_URL=postgresql+asyncpg://postgres:pw@localhost:5555/rumia_restore uv run alembic upgrade head
DATABASE_URL=postgresql+asyncpg://postgres:pw@localhost:5555/rumia_restore uv run alembic downgrade 0007
DATABASE_URL=postgresql+asyncpg://postgres:pw@localhost:5555/rumia_restore uv run alembic upgrade head
docker rm -f rumia-scratch-pg17
```

`alembic/env.py` reads `DATABASE_URL` through the app settings. Upgrade, downgrade and re-upgrade must all succeed.

## 3. Apply (on the server)

```bash
cd ~/rumia
scripts/migrate.sh upgrade
scripts/migrate.sh current        # expect: 0009 (head)
```

## 4. Verify

- Sign in with Google: still works.
- Sign up with email: the 6-digit code arrives (Brevo) and the account is created.
- Sign in with that email and password; use "forgot password" once.
- `docker logs --since 15m rumia_backend 2>&1 | grep -i -E "error|auth_email_codes|auth_credentials"`: nothing new.
- Sentry: no new auth errors.

## Rollback

Code needs no rollback (it is already deployed). If the migration itself misbehaves:

```bash
docker compose exec -T backend alembic downgrade 0007
```

This only drops the two new auth objects; no other data is affected. Restoring the dump from step 1 is the last resort.
