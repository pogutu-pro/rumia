# Proposal 2.3 · Gate deploys on CI and roll back failed ones

Status: **not applied. Needs your explicit approval** because it changes how production deploys. (An attempt to edit `.github/workflows/cd.yml` and `scripts/deploy.sh` was blocked by the safety classifier; this is intentional and I did not work around it.)

## Problem
`cd.yml` runs on every push to `main` regardless of CI (its own comment says "only runs if CI passes", but there is no `needs`/`workflow_run`). `deploy.sh` only warns when the health check fails and cannot go back to the previous version. A broken push reaches production and stays there.

## Change 1: `.github/workflows/cd.yml`
Trigger on CI completing successfully on `main`, and deploy the exact commit CI tested.

```yaml
name: CD (Automated Oracle VPS Deployment)

on:
  workflow_run:
    workflows: ["CI (Automated Testing & Build Verification)"]
    types: [completed]
    branches: [main, master]

jobs:
  deploy:
    name: Auto-Deploy to Oracle VPS (Johannesburg)
    runs-on: ubuntu-latest
    if: ${{ github.event.workflow_run.conclusion == 'success' && github.event.workflow_run.event == 'push' }}
    concurrency:
      group: production-deploy
      cancel-in-progress: false
    steps:
      - name: Deploy to Oracle VPS via SSH
        uses: appleboy/ssh-action@v1.0.3
        env:
          DEPLOY_SHA: ${{ github.event.workflow_run.head_sha }}
        with:
          host: ${{ secrets.ORACLE_VPS_HOST }}
          username: ${{ secrets.ORACLE_VPS_USER }}
          key: ${{ secrets.ORACLE_VPS_SSH_KEY }}
          port: 22
          envs: DEPLOY_SHA
          script: |
            set -e
            cd /home/${{ secrets.ORACLE_VPS_USER }}/rumia
            git fetch origin main 2>/dev/null || git fetch origin master
            git reset --hard "$DEPLOY_SHA"
            chmod +x scripts/deploy.sh
            ./scripts/deploy.sh
```

Note: `deploy.sh` itself runs `git reset --hard origin/main`; change that line to keep the SHA that the workflow already checked out (see change 2).

## Change 2: `scripts/deploy.sh`
- Record `PREVIOUS_SHA="$(git rev-parse HEAD)"` before pulling.
- Replace the git pull step with: only `git fetch`; do not reset (the workflow already set the SHA). For manual runs, keep the current behaviour when `DEPLOY_SHA` is unset.
- Replace the "[4/5] health checks" step: wait up to ~3 minutes for `rumia_backend` and `rumia_web` to report `healthy` via `docker inspect`; if either does not, run `rollback()`: `git reset --hard "$PREVIOUS_SHA"`, `docker compose build`, `docker compose up -d --remove-orphans`, `docker compose restart nginx`, print recent logs, and `exit 1` so the GitHub run fails.

## Consequences
- A failing CI run never deploys. A deploy that does not become healthy undoes itself and shows red in GitHub.
- Rollback rebuilds the previous commit (a few minutes) rather than swapping a stored image. Tagging images by SHA in a registry (GHCR) would make rollback instant; that is a follow-up.
- Database migrations are not part of this yet (no Alembic baseline, see task 2.5); rollback only reverts code.
- First time through, deploy once manually while watching `docker compose ps`.
